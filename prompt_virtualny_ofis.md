# Промт для AI-инструмента разработки (Claude Code / Cursor / Lovable и т.п.)

> Скопируйте текст ниже целиком и вставьте как первое сообщение / project brief в выбранный AI-инструмент разработки. Промт написан с расчётом на кастомную разработку с нуля.

---

## Роль

Ты выступаешь как senior full-stack архитектор и разработчик. Тебе нужно спроектировать и поэтапно реализовать веб-платформу «виртуальный офис» для компании из 20 сотрудников. Перед началом кодирования предложи архитектуру, схему базы данных и план спринтов — и только после согласования переходи к реализации по частям (не пытайся сгенерировать всё одним махом).

## Контекст и цель проекта

Компания из 20 человек хочет заменить разрозненные инструменты (мессенджеры, таблицы, отдельные CRM) единой платформой, где руководитель видит всю картину работы отдела, а каждый сотрудник работает в рамках своей роли и зоны ответственности. Платформа должна быть простой и понятной — приоритет удобства использования выше количества фич.

## Технологический стек (предложение, можно скорректировать)

- **Frontend:** React (Next.js) + TypeScript + TailwindCSS
- **Backend:** Node.js (NestJS) + TypeScript, REST API
- **Realtime:** WebSocket (Socket.io) — для статусов присутствия и уведомлений
- **База данных:** PostgreSQL (основные данные) + Redis (сессии, кэш присутствия, очереди)
- **Файловое хранилище:** S3-совместимое хранилище (MinIO self-hosted или AWS S3) для документов
- **Аутентификация:** JWT + refresh-токены, пароли хешируются (bcrypt/argon2), опционально 2FA (TOTP)
- **Развёртывание:** Docker + docker-compose, Nginx как reverse proxy, HTTPS (Let's Encrypt)
- **AI-интеграция:** Anthropic Claude API — вызовы только через backend (ключ API никогда не попадает на frontend)

## 1. Аутентификация и роли

- Вход только через браузер Chrome по логину (нику) и паролю.
- Роли: **Директор** (полный доступ), **Руководитель отдела** (видит и настраивает своих подчинённых), **Сотрудник** (ограниченный доступ по своей зоне).
- У каждого пользователя — профиль-карточка: специальность, должностная инструкция (текст/файл), список KPI с метриками и сроками. Эти поля задаёт директор или руководитель отдела.
- Права доступа — комбинация роли и уровня записи (RBAC + record-level access): руководитель видит данные только своего отдела, сотрудник — только свои.
- Опционально: 2FA для ролей с доступом к CRM.

## 2. Статус присутствия («зелёная/красная точка»)

- Через WebSocket-соединение и heartbeat (пинг каждые 30–60 сек) отслеживается активность сессии в браузере.
- Зелёная точка рядом с ником — активная сессия/пользователь за компьютером; красная — оффлайн или неактивен дольше заданного порога (например, 5 минут без активности).
- У директора — отдельный дашборд «Кто в сети»: сетка/список всех сотрудников с индикаторами в реальном времени.
- Хранить историю входов/выходов (лог) для последующей аналитики (см. раздел AI).

## 3. База документов компании

- Отдельный модуль «Документы» с папками/категориями (по отделам, по типу: инструкции, шаблоны, регламенты и т.д.).
- Доступ к папкам и файлам регулируется правами роли — часть документов видна всем, часть только определённым ролям/отделам.
- Поддержка загрузки/скачивания/предпросмотра основных форматов (PDF, DOCX, XLSX, изображения).
- Версионность файлов (кто и когда изменил) — желательно.

## 4. CRM-система

**База клиентов и карточки:**
- Карточка клиента: контакты, источник лида, статус, история сделок, прикреплённые документы, комментарии, ответственный сотрудник.
- Каждый сотрудник видит **только своих** клиентов; руководитель отдела — клиентов своей команды; директор — всех.
- **Копировать/экспортировать базу целиком может только директор.** Технически: массовый экспорт (CSV/Excel, bulk copy) доступен только роли «Директор»; для остальных ролей — запрет на массовое копирование, ограничение экспорта только по своим карточкам.

**Защита от взлома и утечки:**
- Шифрование данных в базе (at rest) и при передаче (TLS).
- Аудит-лог: кто, когда и к какой карточке клиента обращался, кто пытался экспортировать данные.
- Rate limiting и защита от bulk-скрейпинга (ограничение количества запросов/просмотров карточек за короткий период).
- Защита от брутфорса при входе, блокировка после N неудачных попыток.
- Регулярные зашифрованные бэкапы.

**Воронка продаж:**
- Kanban-доска сделок со стадиями: Заявка → Оплата → Отгрузка (стадии должны быть настраиваемыми — добавление промежуточных этапов, например «Переговоры», «Счёт выставлен»).
- Каждая сделка привязана к карточке клиента и ответственному.

**Напоминания:**
- Напоминания по срокам сделок/задач с уведомлением в интерфейсе и опционально в Telegram/почту.

**Отчёты:**
- Конструктор отчётов: руководитель выбирает сотрудника, метрики (выполнение KPI, количество сделок, конверсия воронки и т.д.), период и периодичность (ежедневно/еженедельно/ежемесячно) — отчёт формируется автоматически и доступен в личном кабинете руководителя.

## 5. Личная Kanban-доска сотрудника

- У каждого сотрудника — своя доска задач (колонки по умолчанию: «Нужно сделать» / «В работе» / «Готово», с возможностью кастомизации).
- Задачи может ставить руководитель или сам сотрудник; задачи можно связывать со сделками из CRM.
- Своевременное закрытие задач учитывается в рейтинге сотрудника (см. раздел 7).

## 6. Интеграция с AI (Claude)

Backend должен иметь модуль интеграции с Anthropic Claude API (server-side, ключ хранится в переменных окружения). Функции AI-модуля:

- **Оценка работы сотрудника** по заданным критериям (роль, KPI, история задач/сделок) — рекомендации и исправление ошибок в отчётах/документах.
- **Советы**, адаптированные под роль сотрудника (например, разные рекомендации для продавца и для бухгалтера).
- **Прогнозы**: прогноз выполнения плана продаж на основе данных воронки, прогноз загрузки отдела.
- **Оповещения руководству**: AI анализирует поведенческие сигналы (не содержимое личных переписок, а системные метрики — попытки массового экспорта клиентской базы, аномальная активность вне рабочих часов, длительное отсутствие «зелёной точки» при незакрытых задачах, систематические просрочки) и формирует предупреждения о возможном саботаже, утечке информации, халатности или прогулах. Это должна быть комбинация rule-based триггеров + AI-суммаризация для руководителя, а не автоматическое чтение личной переписки сотрудников.

> ⚠️ Важно заложить в архитектуру: уведомить и получить согласие сотрудников о том, какие именно метрики отслеживаются (присутствие, метаданные о доступе к CRM и т.д.) — это не только этично, но и требование трудового законодательства во многих юрисдикциях. AI не должен анализировать содержание личных сообщений сотрудников без явного согласия.

## 7. Достижения и рейтинг сотрудника

- Личный раздел «Мои достижения»: бейджи/значки за результаты (например, «10 задач подряд в срок», «Лучший результат месяца», «Ноль просрочек за квартал»).
- Общий рейтинг успешности — числовой показатель, рассчитываемый по формуле на основе % выполненных KPI точно в срок за период (веса метрик настраиваются руководителем).
- Рейтинг и достижения видны самому сотруднику (мотивация) и руководителю/директору (для оценки).

## 8. Интеграции с почтой и мессенджерами

- **Gmail** — через Gmail API (OAuth2, подключение личного аккаунта сотрудника).
- **Outlook** — через Microsoft Graph API (OAuth2).
- **Telegram** — через Bot API (привязка личного чата или общего бота компании).
- **WhatsApp** — через WhatsApp Business Platform (Meta Cloud API); учесть требования верификации бизнес-аккаунта.
- **Viber** — через Viber REST API (Business Messages).
- Единый модуль «Сообщения» внутри платформы: входящие/исходящие сообщения из подключённых каналов, с возможностью привязки переписки к карточке клиента в CRM.
- Подключение каждого канала — по отдельному OAuth-согласию пользователя (кроме общих корпоративных каналов, которые настраивает директор/админ).

## 9. Требования к UI/UX

- Минималистичный, понятный интерфейс: боковое меню с разделами — Дашборд, CRM, Канбан, Документы, Команда (присутствие), Отчёты, Сообщения, Профиль.
- Дашборд директора: сетка присутствия (зелёные/красные точки), сводные показатели по компании, последние AI-уведомления.
- Приоритет — десктоп/Chrome, адаптивность под мобильные — вторично.

## 10. Нефункциональные требования

- Расчёт на 20 пользователей, но архитектура должна масштабироваться без переписывания (до 100+ пользователей).
- Целевое время загрузки страницы — до 2 секунд.
- Резервное копирование данных не реже 1 раза в сутки.
- Логирование всех действий с чувствительными данными (CRM, документы) для аудита.
